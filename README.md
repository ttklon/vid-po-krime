# Видео по Крыму

## Загрузка больших видео

```sh
python3 upload_server.py
```

Откройте сервер на порту `8080` с фрагментом `/#ключ`, который он напечатает при запуске. Сервер слушает `0.0.0.0`; для внешнего доступа используйте HTTPS-прокси. Можно задать `PORT`. Требуются Python 3.11+, `git`, авторизованный `gh`, доступ на запись в репозиторий и настроенный автор Git. Перед первой загрузкой текущая ветка должна быть отправлена в `origin`.

**Репозиторий публичный. Загруженные видео станут общедоступны!** Перед началом пользователь должен поставить отдельную отметку согласия. Удаление файла из последнего коммита не удаляет его из истории. Не загружайте приватные видео.

### Как устроено сохранение

- Браузер передаёт два файла параллельно частями по 4 МиБ. Каждая часть проверяется по SHA-256 и подтверждается после `fsync` данных.
- При потере связи часть повторяется; сервер не добавляет её дважды. После перезагрузки страницы выберите те же исходные файлы — сервер вернёт подтверждённое смещение. Пауза действует после текущей части.
- Каждый исходный файл должен быть **меньше 2 ГиБ**. Можно выбрать все 11 роликов одновременно; общий объём ограничен свободным местом сервера. На приёме проверяется запас места для входных данных, рабочих копий и Git.
- Как только ролик полностью принят, фоновый обработчик делит его на неизменённые бинарные части **по 48 МиБ** в `media/<upload-id>/part-NNNNN`. Это ниже лимита обычного GitHub-файла (100 МиБ). Это не перекодирование: качество и все байты сохраняются.
- Каждые четыре части (не более 192 МиБ исходных данных) коммитятся и сразу отправляются через `git push origin <текущая ветка>`. Так ни один push не приближается к ограничению GitHub в 2 ГиБ. Резервное копирование файлов выполняется последовательно, приём следующих роликов идёт параллельно.
- После всех частей создаётся отдельный `videos/<upload-id>.json`: исходное имя, размер, SHA-256 всего видео, порядок частей, размеры и хеши частей. Он коммитится и отправляется отдельным push. После каждого push сервер сверяет SHA текущего коммита с удалённой веткой.
- Только после успешной отправки всех частей и манифеста появляется **«Сохранено в GitHub»**. Существующие чужие staged-файлы в автоматические коммиты не включаются. При ошибке push зелёный статус не ставится. Кнопка «Повторить сохранение» повторяет процесс; неизменённые части не создают дублирующих коммитов.
- Данные, ключ доступа и состояние хранятся локально в `.cache/video-upload/` (не в Git). После перезапуска того же сервера на том же диске активное резервное копирование продолжается. **Временный диск среды не является резервной копией**; до зелёного статуса сохраняйте оригиналы и не выключайте среду. Ошибки повторяются вручную.
- Ссылка страницы содержит секретный ключ в URL-фрагменте. Он не передаётся в URL HTTP-запросов или Referer. API требует `Authorization: Bearer …`. Не делитесь этой ссылкой: доступ позволяет загружать файлы и автоматически создавать публичные коммиты.

Для 1,5–2 ГБ видео Git-репозиторий получится большим: клонирование потребует соответствующего места и времени. Этот способ выбран по запросу сохранения непосредственно в коммитах: адрес загрузки вложений GitHub Release в среде недоступен. Git LFS не используется.

Локальные исходники не удаляются автоматически даже после успешного сохранения. Не включайте `.cache/` в Git. Бинарные части в `media/` — намеренные резервные копии пользователя, а не артефакты сборки.

## Восстановление оригиналов

Склонируйте репозиторий и нужную ветку, затем выполните:

```sh
python3 restore_video.py videos/*.json --output restored
```

Либо укажите один манифест. Скрипт собирает части в указанном порядке, проверяет хеш каждой части и всего видео, восстанавливает оригинальное имя и не перезаписывает существующие файлы. Восстановленные видео игнорируются Git.

## Тесты

Без отправки тестовых данных в GitHub:

```sh
python3 -m unittest discover -s tests -v
```
